## Permission model in implementer/reviewer sessions
Implementer and reviewer agents almost never get full tool access — usually just file writes or read-only shell commands. When that happens, don't report `BLOCKED` just because `bun test` or `bun run typecheck` couldn't actually run. Trace the change by hand, say exactly what's unverified, and report `DONE_WITH_CONCERNS` instead.

This has held across many sessions now (task archiving, dependsOn/supersededBy fix, model-selection SDD) and is proven durable: a later reviewer or CI pass always runs the real suite before merge, so tracing by hand and flagging the gap is the correct move, not a workaround. The one nuance worth remembering: sandboxes vary in *what* they block — sometimes it's `bun test`, sometimes it's `git add`/`git commit`, sometimes it's a paid subprocess spawn (e.g. an eval that shells out to a real `claude` call). Whatever the specific denial, the response is the same: hand-trace, name the gap precisely, report `DONE_WITH_CONCERNS`, and let the next stage (reviewer/CI/a session with commit access) do the real verification.

## Review process: re-verify claims, don't trust them
When you're reviewing someone else's work (including a prior review pass), check every factual claim yourself instead of taking it at face value. A claim like "grep found nothing relevant" or "this citation is accurate" is only as good as the person who ran it.

This keeps paying off concretely: one reviewer asserted a grep came up empty and was wrong, caught by the next review round grepping independently. On the model-selection SDD, an independent citation check caught two real defects a first pass missed — a false claim that `anthropic-api.ts` already had a `this.model` constructor override (it didn't; the other four executors did, this one didn't), and a quote misattributed to the wrong section of another doc. On the task-archiving feature, a second review round didn't just re-run the test suite, it re-read the diff line by line and independently confirmed the first round's fix actually closed the gap it claimed to close. The pattern: when reviewing, re-run the specific check the prior pass claims to have done — don't just check the conclusion.

## Changing `TaskCard.status` (adding a new status value)
If you ever add a new status value to task cards, there are exactly two files that must move together: `src/core/types.ts` (the status union) and `src/api/public/board.html`.

`board.html` enumerates the full status list in three separate literals — `STATUS_COLOR`, `STATUS_LABEL`, and the `COLUMNS` array. Missing any one of the three means a task silently disappears from the Kanban UI or renders with a blank/`undefined` style. No other code does an exhaustive switch over status (everything else is `===`/`!==` comparisons), so these two files are the complete surface — but this has been missed on the first pass more than once, so treat it as a checklist, not a memory jog.

## Output contracts for agents whose raw response becomes data
Any agent whose final message gets parsed as data rather than just displayed — a verdict, a structured plan, a wholesale file replacement — needs an explicit `outputContract` in `agents/manifest.yaml`, wired through `buildAgentPrompt`, plus a parser that fails closed. Never default to "approve" or "success" or "empty plan" on missing/malformed output.

`reviewer` uses `parseReviewVerdict`. `memory-curator` uses a prose-discipline contract (no JSON, no fences, no preamble — first character of the message is the first character of the file) because its payload is markdown, not structured data. `planner` now uses the same discipline as `reviewer` for its subtask-decomposition output: `parseSubtaskPlan` mirrors `parseReviewVerdict` case-for-case (last-fenced-block-wins, rejects any `dependsOnIndex` that's forward, self-referencing, negative, or non-integer, fails closed to `null` rather than partial-parsing). Three agents now share this convention — when adding a fourth, copy `parseReviewVerdict`'s shape rather than inventing a new one. All of these were caught missing in initial review passes before being added, so don't assume a new agent has one by default — check.

## SDD / doc citation discipline
Never cite a spec doc's sections, line numbers, or quotes as authoritative unless you've actually checked them against the current repo state. Citations drift, and reviewers check every one of them.

Concrete failure modes caught in review, more than once each: `docs/SDD-memory-curator.md` was cited by name and section before the doc existed, twice, both caught. A dangling `§9` reference and a wrong line number were both caught twice in the same doc. On `SDD-model-selection.md`, review caught a false claim that "every executor already has a `this.model ?? agent.costProfile.model` override" — `anthropic-api.ts:86` was cited as proof, but that file's `ApiExecutorOptions` has no `model` field and line 86 is a bare, unconditional assignment; the other four executors (`readonly.ts`, `write.ts`, `codex-write.ts`, `codex-readonly.ts`) do have the override, this one didn't yet. Same doc had a quote lifted from `SDD-new-task-tab.md` §8 but attributed to §1. Both were fixed and re-verified clean on the next pass. Takeaway: verify every citation — code line, doc section, and quoted text — before submitting, not just the prose structure around it.

## SQLite schema changes
New columns on existing tables use the established heal-on-open pattern: `ALTER TABLE ... ADD COLUMN` wrapped in try/catch at DB-open time, matching the `harness`/`parentTaskId` precedent in `src/services/board.ts`.

`ADD COLUMN` in SQLite is always safe (nullable, no data loss on existing rows), so no separate migration tooling is needed. The task-archiving feature's `doneAt`/`archivedAt` columns followed this exact pattern and it held up through review with no changes requested — this is a confirmed-good approach, not just a theoretical one.

## Worktree/lineage keying, `supersededBy`, and `dependsOn`
Pushback retries key their worktree off `reviewLineageId ?? task.id` in the write executors, so repeated re-attempts reuse the same worktree/branch — one `git worktree add` total across N attempts, not N. A human-triggered "restart" after escalation instead mints a brand-new `reviewLineageId` rather than reusing an exhausted one — "restart, not silent extension" is the intended distinction between these two paths.

`supersededBy` never touches `status` — a superseded card keeps its old status forever by design; the old card isn't meant to be resurrected. This used to cause a real bug: `sweep()`'s dependency check looked at a dependency's literal `status`, so once a card got pushed back and superseded, anything that `dependsOn` it stayed blocked forever even after the real re-attempt reached `done`. Fixed via `resolveLiveTip(task, byId)` in `src/core/orchestrator.ts` — follows the `supersededBy` chain forward to whatever card is actually alive, with a visited-set cycle guard that fails closed (treats a cycle or dangling pointer as still-blocked, never as satisfied). `sweep()`'s blocked-check and `board.html`'s "⛔ Depends on" tag rendering both now resolve through this before reading status/title. Remaining known gap, not yet addressed: `board.html`'s kanban *column* rendering still doesn't filter superseded cards out of their old column, so a stale-looking duplicate can remain visible there after a retry — distinct from the dependsOn-tag fix above, and still open.

## Wiring UI actions to endpoints
Before wiring a button to a `POST` endpoint, check what request body the endpoint actually requires. A bare `fetch(url, {method:"POST"})` with no body silently 400s against any endpoint that requires fields.

This shipped once for real (escalation approve/retry buttons) and needed a dedicated follow-up fix plus real dialog-driven e2e tests — not just visibility assertions — to catch it going forward. When adding a new button-to-endpoint wiring, write the e2e test around the actual dialog/data flow, not just "the button exists and is clickable."

## `parentTaskId` is overloaded — don't assume it's just for display
`parentTaskId` on a `TaskCard` does two unrelated things at once: it's used for UI grouping/display (e.g. showing a pushback re-attempt under its original), and it also feeds `resolveHandoffAllowlist`, which restricts a routed task to *only* the parent's declared `handoffs` list in `agents/manifest.yaml`. If you set `parentTaskId` for display purposes on a task whose real target isn't in the parent's `handoffs`, that task silently routes to `no-match` and never dispatches.

This is a real, currently-unfixed bug: `spawnSubtasksFromPlan` (`src/core/orchestrator.ts`) sets `parentTaskId: plannerTask.id` on every child it creates from a planner's decomposition. Planner's manifest entry declares `handoffs: [implementer, reviewer, integrator]` — a list that predates the subtask-plan feature. Any spawned subtask labeled for an agent outside that list (e.g. `fixer` via `["ci","tests","bugfix"]`, or `pr-description-writer` via `["docs","pr"]` — both explicitly recommended by the planner's own contract text) gets filtered out as a routing candidate before tag-overlap scoring ever runs, and silently dead-ends on `no-match`. Reviewer flagged this with a live reproduction against the real registry/board and requested changes; as of the last session on this card it was still unresolved, needing an explicit decision: either widen planner's `handoffs` to cover every agent a subtask might target (brittle, has to stay in sync with the contract's label guidance), or stop applying the handoff-allowlist restriction to `spawnSubtasksFromPlan`'s children entirely (since `parentTaskId` there is for grouping, not a real handoff relationship). Anyone touching `parentTaskId` semantics or planner subtask-spawning should resolve this, not just work around it.

## Test fidelity: exercise the real dispatch path, don't hand-build the state
A test that calls an internal function directly with a hand-built object can look like it's testing production behavior while actually skipping the exact guard condition the bug lives in.

Concretely: `test/orchestrator.test.ts`'s subtask-plan test called `finishResult` directly with a synthetic `TaskResult`, without first routing the planner task through a real `sweep()`. In production, `sweep()` stamps `routedTo` on the planner task *before* `finishResult` runs, and that `routedTo` is exactly what feeds `resolveHandoffAllowlist`'s restriction (see the `parentTaskId` lesson above). Because the test skipped that step, `plannerTask.routedTo` was `undefined` when `spawnSubtasksFromPlan` ran, so the allowlist check returned "unrestricted" instead of the real `[implementer, reviewer, integrator]` restriction — meaning the test's `not.toBe("done")` assertion passed regardless of whether the bug was present. When a test needs to assert on routing/dispatch behavior, drive it through the real `sweep()` first so the state it asserts against matches what production actually produces.
